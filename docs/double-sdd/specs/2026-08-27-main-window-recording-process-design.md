# 主应用录音与界面绘图双进程设计

## 1. 状态与背景

- 日期：2026-08-27。
- 设计依据：用户已确认双进程范围、兼容要求、累计波形行为及录音进程异常处理，并同意进入规格编写。
- Recorded base: `e8990f1fbe13d7dd0f0bf23973b56c653d92f72e`。
- 本文是实现前规格；不代表代码已修改或验收已经通过。书面规格仍需用户最终审阅。

应用入口为 `main_window_Launcher.py`，经 `MainWindow` 创建 `SequenceWindow`。当前普通录音在 `_start_blocking_recording` 中同步调用 `SoundcardAudioProcessor.sd_rec`；流式录音由 `StreamingAudioProcessor` 的声卡回调产生音频，再通过进程内队列和全局 Qt 信号交给 UI。UI 消费队列、积累完整音频、写 WAV、累计波形，并在完成时裁剪启动瞬态、追加校准元数据、更新分析数据及数据库。

因此只将设备回调包装进 `multiprocessing.Process` 不够：若完整数据仍依赖 UI 消费和写盘，界面繁忙仍会拖延保存。现有 `MultichannelWaveformSession` 和 `StreamingWaveformAccumulator` 已提供覆盖本轮全部时间范围、每通道最多 4000 点的累计峰值包络，可复用其纯计算逻辑。

## 2. 已确认需求与范围

1. 只拆分 Launcher 启动的应用。`record_vkinging_continuous.py`、其副本和 Vkinging 独立录音入口不改。
2. 主进程保留全部 Qt 窗口、绘图、配置、条码/工况流程、数据库和分析；独立录音子进程负责设备采集、实时监听、音频缓存、WAV 内容写入及收尾。
3. 主界面的普通录音和流式录音全部覆盖。输入校准复用同一录音服务，校准计算和校准 JSON 保存仍在主进程。
4. 保持现有操作、配置、多通道顺序、启动裁剪、监听增益和静音/淡入、校准含义、WAV 格式及成功录音的分析结果兼容。
5. 繁忙时可跳过中间刷新次数，但不能跳过录音数据或丢失某一段历史波形。恢复时更新累计波形，结束后显示整段最终录音。
6. 录音子进程意外退出导致尚未成功接收的本轮失败：不入库、不分析，不自动续录，不拼接前后两次录音；提示后允许用户重新录音。

非目标：迁移 AI/FFT 等分析计算进程、重做窗口布局、改变结果判定、改动独立播放/输出校准的播放链路、重构导入音频或导出功能、支持远程录音服务、保证断电恢复。本任务消除采集/保存对 UI 消费的依赖，不宣称分析计算本身从此不会阻塞界面，也不宣称能够克服磁盘满或声卡硬件溢出。

## 3. Compatibility / Migration

- Backward compatibility: required
- Protected surfaces: `[Launcher 启动方式, 用户配置与默认值, 普通/流式选择, 实时监听, 物理输入通道与 WAV 列映射, 采样率与有效录音时长, 启动裁剪和监听静音/淡入, 输入校准算法与 JSON, WAV float32 音频和现有校准 RIFF 元数据, 成功文件路径和命名, 重录使用同一路径, 数据库 schema, 条码及手动/串口工况流程, 历史波形及分析结果, 独立录音脚本]`
- Allowed breakage: `[私有进程内队列/信号及 processor 实现可替换; 普通录音内部不再阻塞 Qt 事件循环; 子进程死亡和确定的数据丢失不能按成功录音处理; 启动裁剪写回失败由原先仅日志降级改为本轮失败，以满足写盘失败不进入分析的已确认规则]`
- Migration strategy: none

不新增用户必须配置的进程选项，不迁移配置、数据库或已有 WAV。保留当前有效模式判定 `bool(use_streaming_recording or monitor_playback)`：两者都关闭时是普通录音，不显示实时波形，完成后展示最终波形；任一开启时使用流式录音并实时显示累计波形。即使旧配置同时包含 `use_streaming_recording=False` 和 `monitor_playback=True`，运行时仍按流式监听执行。配置窗口关闭流式开关时清除/禁用监听的现有交互不变；监听仍遵守设备组合限制。

旧全局 Qt 信号不是跨进程协议。可为尚未迁移的内部调用保留进程内兼容入口，但 Launcher 的主录音和输入校准实际采集不得回退到 UI 进程。已有低层声卡帮助方法可继续服务独立调用，不作为本次主应用路径的静默降级。

## 4. 方案选择

| 方案 | 取舍 |
| --- | --- |
| **录音子进程独立写盘，发送累计波形快照和完成结果（采用）** | 录音/写盘不等待绘图；实时传输量与显示点数而非录音总长度相关；可复用累计包络；正常分析只在完成后读一次全量结果。 |
| 子进程逐块传原始音频，由主进程保存 | 改动较少，但保存仍依赖主进程消费，不满足已确认边界。 |
| 共享内存环形缓冲传全部原始音频 | 复制开销较小，但增加覆盖保护、读写同步和异常资源回收复杂度，本次无必要。 |

采用标准库 `multiprocessing.get_context("spawn")` 和显式消息通道，不使用 `Manager` 或进程池增加辅助业务进程。主应用同时最多持有一个录音子进程和一个活动采集会话。子进程首次使用时启动，健康时跨多轮复用，不每次录音重新创建解释器。

## 5. 组件及责任

### 5.1 主进程服务与 UI 适配

应用级 `RecordingService`（名称可随实现规范调整）由 Launcher/主窗口生命周期显式持有，并传给主录音和输入校准调用者；不在模块导入时创建全局服务或启动进程。

服务负责启动、会话注册、命令发送、消息接收、子进程存活监测、最终文件读取以及资源回收。UI 适配层将普通 Python 消息转成主进程内的 Qt queued signals。接收、发送、文件读取及进程等待使用主进程中的后台线程，不能在 Qt 主线程阻塞 `recv`、`send`、`join` 或读取大录音文件。

录音请求提交前先登记会话及其 UI 处理对象，再发出启动命令，防止短录音的完成通知早于 UI 绑定。服务具有明确的 starting/busy 状态；未收到成功或失败的启动结果前不能再次开始录音。服务握手、每轮打开设备及每条取消路径分别有 §8.2 的有限期限，不能因为健康 worker 卡在 native 调用中而永远 busy。不同调用者同时申请设备时明确提示设备忙，不抢占或静默取消已有录音。

主进程继续保存配置、条码、工况、标签、报告和分析的权威状态。子进程不访问 `DataDealStruct`、数据库、QWidget、全局 Qt signal bus 或可变 UI 配置。

### 5.2 录音子进程

子进程的可导入顶层入口仅接收可序列化启动参数和同一 spawn context 创建的 IPC 对象，独立创建声卡客户端、流、日志、缓存和文件 writer；不传递父进程中的 stream、锁、QObject、打开的文件或闭包。

子进程内部允许声卡回调线程、音频消费线程和命令/消息线程，但全部实际录音与录音文件内容写入都在该 PID 内。采集回调只完成必要的通道选择、拥有独立内存的音频复制、准确计数、非阻塞入队和实时监听输出；不得在回调里绘图、写盘、发送 IPC 或等待 UI。

按同一通道快照执行单/多通道采集。有效模式为普通录音时可复用同一回调采集核心但关闭实时快照；内部不必继续使用阻塞 `sd.rec`，前提是采样数、dtype、通道选择、录音结果和 §3 的模式判定保持兼容。`LoadUiConfig.get_rec_and_play_dict_base_sequence_dict` 当前主界面请求固定 `prolong_frames=0`，新协议据此保持同等目标计数；不改变低层 `sd_rec` 独立调用中非零 `prolong_frames` 的处理，产品启动裁剪仍只应用一次。

纯波形累计算法放在不导入 Qt 的基础模块；必要时由原 UI 模块重导出以保护现有引用。只做实现进程隔离所需的定向抽取，不顺便重构整个声卡、校准或分析模块。

### 5.3 设备与配置快照

每轮请求是独立值对象，至少包含：会话 ID、用途（主录音/输入校准）、普通/流式模式、输入设备描述与索引、输入通道有序 tuple、输出设备和监听通道、采样率、目标原始样本数、启动裁剪样本数、监听增益/静音/淡入、音频有效性阈值、最终绝对路径以及本轮 WAV 校准元数据快照。

子进程独立初始化声卡环境，包括已有 ASIO 开关；不依赖父进程修改的 `sd.default`。在打开流前检查请求设备身份、当前索引及通道范围。设备消失或索引指向不同设备时返回诊断错误，不静默换设备。设备选择 UI 和原有恢复规则仍在主进程；新配置只作用于下一轮。

输入校准请求保持当前单个物理通道、44100 Hz、10 秒的采集语义，无实时波形，不使用产品录音的启动裁剪或产品音频质量阈值。计算 SPL、v2pa、保存校准 JSON、切换下一待校准通道的现有逻辑不变。

## 6. 音频、保存与最终结果

### 6.1 完整音频链路

声卡回调按 `(frames, selected_channels)`、`float32` 顺序产生拥有自身存储的块。复用驱动缓冲后不得改变已入队音频。最后一块只接纳达到目标所需的样本，不多写、不重复写。

子进程音频队列按字节/样本设置有限容量，基准容量为约 2 秒当前采样率和通道数的音频，至少容纳一个回调块；实现必须公开可测试的容量计算，不依赖 `qsize()` 作正确性判断。消费线程持续按顺序写文件和更新包络，与父进程是否读取快照无关。

队列饱和或设备报告确定的输入 overflow 意味着完整性无法保证：标记本轮失败、停止流、输出诊断，不丢掉一个块后继续宣称成功。不用无界队列掩盖磁盘过慢。普通输出状态警告与输入丢样分开处理；不得将所有声卡状态一概改为失败。

### 6.2 文件单一所有者

主录音的 writer 创建、逐块写入、关闭、启动裁剪重写及 WAV 校准元数据追加都由子进程完成。主界面不再创建 `StreamingWavWriter`，也不在 chunk/完成回调中保存或重写本轮音频。

保留现有最终路径、命名、float32 WAV 以及重录路径复用行为。允许为裁剪重写创建本轮专有临时文件，成功关闭后替换；只清理本轮拥有的临时文件，不扫描删除目录中的其他文件。子进程持有写句柄或父侧仍有 §6.4 的交付读租约时，禁止提前重命名、打标移动、删除或开始同路径重录。

自然完成顺序：

1. 停止设备接受新块并关闭输入/监听流；音频消费者排空全部已接受块。
2. 核对 raw accepted/written 数和目标计数，完成原始 WAV 收尾。
3. 按本轮已解析的规则执行启动裁剪，保持目标有效时长。裁剪为 0 不改数据；裁剪量不小于全部数据时沿用当前跳过裁剪并警告的行为。
4. 用现有 `validate_recorded_audio` 和本轮阈值校验最终主录音，不另起一套信号判定。无效音频走既有无效录音流程。
5. 在最终音频上追加已捕获的 WAV 校准元数据。保持当前元数据附加函数的警告契约：缺少快照或返回“未附加”时随结果传递警告，不伪称已有元数据；音频本身不可读取/关闭失败仍是录音失败。
6. 关闭全部本轮子进程文件句柄，发送完成描述及写入所有权释放状态；父侧随后可按 §6.4 获得读租约，不能把“子进程已关闭”误认为整个交付已经结束。

仅在上述必要的音频保存步骤成功后发送 `completed`。不能先让 UI 入库，再异步写盘。UI 不重复裁剪、不再次写元数据、不重复写 WAV。

### 6.3 全量结果交付

主录音完成描述含最终文件绝对路径、采样率、有序物理通道、原始/最终样本数、用途、元数据附加状态和警告。主进程后台读取已关闭的最终 WAV 一次，检查 float32、多通道列数和样本数，再将独立数组交给 UI。mono 仍由最终 multi 按原规则取均值。

UI 校验会话和现有最终波形工作区契约后，才能更新 `DataDealStruct`、方向/工况缓存、最近记录、数据库及分析；保留现有串口/手动工况推进和结果判定。文件读回失败或最终工作区语义不匹配不发布新分析数据，按失败处理。单纯 `set_data`/绘图异常在语义校验通过后只提示波形显示失败，不否定已保存录音。

输入校准没有用户录音保存路径：子进程将完整 float32 结果写到父服务预先分配的本轮临时目录，使用无损临时文件交付，避免把大数组加入控制消息。主进程读取后计算校准；临时文件不加入产品录音目录、数据库和最近记录，完成/失败/取消时按会话所有权清理。

子进程不通过 IPC 传输整段原始数组或不断增长的原始历史；录音期间原始数据主要在文件中。最终校验和分析允许有与单次完整录音大小相关的数组，但不得每次刷新重建历史数组。

### 6.4 父侧交付读租约与清理

服务从提交 start 起为本轮绝对路径登记独占租约；收到子进程写句柄释放的终态后，后台 reader 才能打开结果。读租约由服务持有，直到 reader 在 `finally` 中关闭全部文件/mmap 句柄并明确报告退出。交给 UI 的是独立数组，不携带仍映射到文件的视图或打开的 reader。

delivering 期间取消、关闭校准窗口或读回失败时，先标记本轮拒绝接纳并撤销后续 UI 完成回调，再请求 reader 合作取消；分块读回在块间检查取消标记。等待 reader 关闭句柄之前，不清理临时目录、不移动/删除结果，也不允许相同路径再次录音。UI 本身不阻塞等待 reader。

父侧 `result_ack` 包含 accepted/rejected 处置。正常接纳需读回完成并通过 UI 语义校验；拒绝结果需 reader 已退出。两种 ack 都只在父侧文件句柄关闭之后发送。子进程若已死亡则无需发送 ack，但仍必须等待父侧 reader 退出才释放文件租约。子进程进入 delivering 后不能自行删除或重写交付文件；收到 cancel 也只标记取消，文件清理由父服务在所有句柄释放后统一调度。

校准临时目录归父服务所有：子进程关闭写入、父 reader 退出后由父服务清理，覆盖成功、失败、取消和应用退出。主录音失败文件仍按现有无效录音策略清理，取消文件按 §8.1 保留收尾行为；清理者必须检查会话租约，不能作用于已被新会话复用的路径。

普通的 reader 取消在基准 5 秒内结束。若操作系统文件 I/O 无法及时返回，界面仍报告取消/失败，服务不无限等待；该具体路径进入“尚待释放”状态，明确拒绝相同路径重录/移动/删除直到 reader 实际退出。由于此时不能向等待交付的子进程发 result_ack，父服务按 §8.2 终止并回收旧 worker，而不是清空其 busy 后继续复用。不同路径的新录音可以在子进程已回收后开始。迟到的 reader 只能关闭旧会话句柄、执行其被授权的清理，不能发布结果或删除新会话文件。任何残留释放问题必须记录并告知，不假装锁已释放。

## 7. 累计波形与消息协议

### 7.1 “跳过刷新”的精确定义

子进程消费的每一个有效音频块都更新各通道累计峰值包络。快照覆盖从本轮有效录音起点到 `sample_stop` 的完整时间范围，不是最近一块或固定尾部窗口。实时显示跳过启动裁剪区，通道与最终 WAV 一致。

每通道继续使用最多 4000 点、保留首尾与峰值的现有显示规则。显示降采样并不表示 WAV 丢样；也不承诺屏幕上逐个画出所有原始采样点。恢复后图表包含繁忙期间的波形时间范围和对应包络，最终全量数据按现有最终绘图算法展示。

快照独立拥有数组存储，包含会话 ID、worker generation、递增 snapshot sequence、sample_stop、通道顺序和每通道 time/amplitude。禁止把跨多个音频块拼接的增量消息当作可直接覆盖的完整快照。

### 7.2 有界快照传输

控制/生命周期事件与预览分开传输。快照采用单份在途 credit/ack：父进程消费或明确丢弃一份快照后才允许下一份；子进程在等待 credit 时仍继续采集、写盘和累计包络。再次允许发送时现场生成当前累计快照，不补播过期快照。

快照发送使用独立发送路径，不在音频回调/文件消费线程上阻塞。子进程待发和父进程待绘制各最多保留一份快照，不保留历史消息队列。使用 queued Qt wakeup 时每个活动会话至多排队一个预览唤醒，不得每个声卡块发一个跨进程 Qt 事件。

快照接收和绘图解耦。父进程只接受匹配 worker generation、会话 ID 且序号/sample_stop 不倒退的数据。暂停绘图 1 秒或 30 秒不会使控制通道被波形塞满。最终完成通知不能等待预览 ack；UI 收到最终文件后直接生成权威最终波形，过期快照不得覆盖它。

包络构建或显示出错时仅禁用本轮实时预览并报告一次，写盘继续；最终文件成功读回后仍尝试最终绘图。不把图形异常归为声卡采集失败。

### 7.3 协议与幂等性

内部协议使用版本字段和可序列化的明确消息类型。最少包括：

| 方向 | 消息 | 语义 |
| --- | --- | --- |
| 父→子 | start | 完整请求快照；会话已在父侧登记。 |
| 父→子 | cancel | 取消指定会话；重复请求无副作用。 |
| 父→子 | preview_ack | 已消费/丢弃指定快照，释放下一份 credit。 |
| 父→子 | result_ack | accepted/rejected；父侧读句柄已全部关闭且结果已接纳或明确放弃。 |
| 父→子 | shutdown | 不接收新会话，停止活动会话并退出。 |
| 子→父 | ready / started | 服务就绪；本轮设备实际启动成功。 |
| 子→父 | preview | 当前累计快照。 |
| 子→父 | completed | 音频已保存、文件句柄已关闭的结果描述。 |
| 子→父 | failed / cancelled | 非成功终态；禁止触发成功完成路径。 |

控制通道按单活动会话设计，只允许有限的在途请求和生命周期事件；不承载逐块音频。每个连接端只有一个明确读者、一个串行写者。诊断日志保存在本地，不无限广播到消息通道。

会话状态为 `starting → recording → finalizing → delivering → completed`，任一未终结阶段可进入 `failed` 或 `cancelled`。子进程在 delivering 阶段等待结果交接确认，不接受下一轮采集；正常 result_ack 释放此 busy 状态。所有读写句柄释放及旧会话清理结束之前，父服务不释放同路径租约。父侧在结果读回、语义校验并接纳后封存终态，每轮只允许一次完成/失败分派。失败/取消回调可以先恢复 UI 状态，路径复用仍受读租约约束，不能用重置 busy 标志替代文件释放。

子进程死亡若发生在父侧接纳完成之前，本轮失败，即便磁盘上已有文件也不自动入库；接纳完成之后的服务死亡不追溯作废已完成录音，但下一轮必须创建新的 worker generation。对同一会话的 EOF、死亡通知、failed 消息和重复 completed 去重。取消已接纳完成的会话不倒退其状态。

## 8. 取消、失败与应用退出

### 8.1 取消与失败

取消不等同于自然完成。先阻止新的采集、关闭设备、排空已接受音频并尝试收尾，发送 cancelled，不入库、不分析、不推进成功工况。保持现有人工停止后已接收的主录音文件可被收尾的行为，但不将它作为成功记录；输入校准取消只清理临时结果。若收尾出错，改为 failed 并报告原因。

设备错误、计数/通道契约错误、写盘错误、最终文件读回错误和子进程死亡走一次失败处理：解锁录音/通道/条码状态，撤销当前占位记录，不触发本轮分析或成功统计，保留原有串口产品运行错误处理。无效主录音文件按既有 `_handle_invalid_recording` 行为清理，但必须等子进程已释放文件或确认进程退出后执行。只处理本轮确定的路径；不删除其他记录。

不自动续录或重试失败会话。用户下一次点击录音时，若旧子进程已死或不可用，服务先确认其被回收再创建新 generation；失败会话的旧 IPC 对象、锁和快照全部废弃，禁止复用被强制终止进程使用的通信通道。

### 8.2 生命周期与超时

- 服务启动等待 ready 使用有限超时（基准 10 秒），UI 保持响应；超时只报启动失败，不在 UI 进程回退采集。
- 每轮向健康 worker 发出 start 后，也单独等待 started 或 failed（基准 10 秒），覆盖设备打开卡死。超时使本轮失败并使 worker 不可复用，执行以下终止/回收流程；不能因服务曾经 ready 而取消这轮期限。
- 所有 cancel 路径，包括人工停止、开始新录音前的清理、输入校准窗口关闭、失败后的清理和应用退出，均从发出取消起使用基准 5 秒收尾期限。正常关闭先 shutdown/cancel，在后台等待句柄释放；期限内不能以“取消已收到”代替“设备和写句柄已释放”。
- 收尾期限届满视为本轮失败，终止子进程，再等待最多 2 秒确认退出，必要时使用操作系统强制结束。仅在确认旧 PID 退出后创建新 generation；所有晚到 started/cancelled/failed 消息按会话去重。若操作系统尚未确认退出，明确提示录音服务未释放、禁止重启，并继续非阻塞监测，不无限 `join` 或假装已回收。
- 交付 reader 有独立的 §6.4 取消和读租约规则；终止录音子进程并不会释放父侧 reader 的文件句柄。发生读回取消超时必须隔离具体路径而不是抢先删除/重录。
- 这些超时是实例级可注入参数，以支持确定性测试，不新增用户配置项；实现若设备验证要求调整须在验证记录中说明。
- 主窗口真正退出、Launcher 失败和应用 `aboutToQuit` 路径共享幂等收尾。`MainWindow.init_ui()` 对尚未显示的 SequenceWindow 调用 `close()` 的初始化动作不能误杀应用级录音服务。
- 子进程监测父进程的操作系统存活状态，不使用“UI 心跳超时”判断父进程死亡，否则会误停繁忙界面下的录音。父进程死亡时停止录音并退出；本进程收尾超过相同时间边界时退出进程，避免遗留录音服务。
- 输入校准窗口关闭只取消它拥有的会话，不关闭整个应用级服务；真实应用退出才销毁服务。
- 已有 Excel/PDF 退出保存仍保留，但不得在录音文件尚被子进程占用时触发结果移动或新录音；退出次序和重入必须测试。

强制终止或系统/设备故障可能使最后的文件收尾失败，必须明确报失败，不能承诺此时 WAV 完整。本规格保证正常采集不因 UI 刷新滞后而缺样，不保证断电、磁盘故障或强制结束下的数据恢复。

## 9. Windows 启动边界

`main_window_Launcher.py` 的 `__main__` 中调用 `multiprocessing.freeze_support()` 后再启动 Qt 应用。入口的 UI 导入应延迟到主应用路径，避免 spawn 重导入 Launcher 时初始化 QWidget、启动 splash、加载业务 singleton 或打开硬件。子进程入口位于不导入 UI 的普通模块。

使用局部 spawn context，不在库模块中调用全局 `set_start_method`。不得传递不可 pickle 的测试闭包或 Qt 对象；真实 spawn 测试的 fake backend 也必须来自可导入模块。Windows 源码运行必须实测，若仓库存在可执行文件打包链路则补充打包 smoke；不存在打包环境时不得声称已验证打包运行。

依据：[Python 3.12 multiprocessing 文档](https://docs.python.org/3.12/library/multiprocessing.html#contexts-and-start-methods)。spawn 使用独立解释器，入口需安全导入；进程间队列/管道传递序列化数据，不能把原来的进程内对象共享当作新协议。

## 10. 异常及状态约束

新增异常必须提供语义、诊断或恢复价值，明确附带失败阶段、会话、设备或路径信息。预期的启动/设备/I/O 错误在录音服务边界规范化为失败事件；子进程顶层可捕获未知异常、记录 traceback 并关闭资源。父进程接收器捕获 EOF/BrokenPipe/进程死亡并只发出一次会话失败。

不得在每层重复 `except Exception`、静默吞掉录音失败、以空数组/默认设备伪装成功，或在 UI 和 worker 同时包装同一个失败。绘图、元数据可选附加及录音保存的失败边界按前文区分；新增广泛捕获必须有明确边界和用途。

所有会话状态、generation、队列、进程、事件、超时和文件所有权保存在服务/会话实例，不增加模块级可变运行状态。单次使用的模块级常量禁止新增，除非属于稳定的外部协议、文件格式、环境变量、CLI/API、schema 或序列化状态字段；本地稳定边界可留模块内，需要跨模块/测试/文档引用的稳定协议定义放在合适的 `consts` 目录。普通实现数值使用局部变量或实例参数。

## 12. 完成条件

所选主应用录音与输入校准采集实际发生在独立子进程，主录音 WAV 内容写入不依赖 UI 消费；累计波形在暂停刷新后能补齐；失败/取消/退出和多轮状态可验证；兼容回归与真实 spawn 验证通过，并明确剩余硬件验证限制。只新增 Process 包装或改 Launcher 而保留 UI 写盘，不满足本规格。

书面规格评审及用户确认通过后，才进入 implementation plan；本规格不授权跳过后续计划和实现验证步骤。
